## 1. Resumen Ejecutivo de Seguridad

El microservicio de Segunda Vida y Donaciones (`ms-segunda-vida-donaciones`) gestiona el ciclo transaccional de publicaciones C2C, la vitrina benéfica abierta a fundaciones aliadas y el almacenamiento multimedia en **Azure Blob Storage** sobre **PostgreSQL 16** (`styleradar_donations`). Aplica **Defensa en Profundidad** desde la capa perimetral HTTP hasta la persistencia y mensajería **AMQPS TLS**:

1. **Autenticación Stateless Bearer JWT (`HS256`):** `JwtTokenProvider` y `JwtAuthenticationFilter` validan firma HMAC-SHA256 (`>= 256` bits en Base64 vía `JWT_SECRET_BASE64`), vigencia y normalización multi-rol (`USER`, `STORE`, `FOUNDATION`, `ADMIN`, junto con alias oficiales de `ms-auth`). En perfiles no locales (`qa`, `prod`), el arranque falla explícitamente si falta o es débil el secreto JWT.
2. **Control de Titularidad Anti-IDOR / BOLA (`ResourceOwnershipValidator`):** Todo endpoint que opera sobre un usuario donante, propietario o representante de fundación valida que el identificador autenticado en el token JWT coincida con el dueño del recurso (salvo `ROLE_ADMIN`), y en `POST /api/v1/donations` el `donorId` se deriva exclusivamente del JWT ignorando valores arbitrarios enviados en el cuerpo JSON.
3. **Verificación Autenticada de Fundaciones y Regla Anti-Autodonación:** `TiendasFoundationCatalogAdapter` exige canales autenticados (`/api/v1/internal/foundations/{id}`, `?representativeId=` con Basic Auth o `/api/v1/foundations/representative` con Bearer JWT) para resolver `representativeId` y prohíbe al propietario reclamar o autoaprobar sus propias prendas (`AntiSelfDonationRule`).
4. **Cero Exposición de Credenciales y Perfiles Productivos Endurecidos:** En `qa` y `prod`, los endpoints `/api/v1/auth/**` están deshabilitados mediante `@Profile` y `SecurityConfig`; las credenciales de PostgreSQL, RabbitMQ (`AMQPS :5671`), Azure Blob Storage y `ms-tiendas` se inyectan exclusivamente por variables de entorno / GitHub Secrets.
